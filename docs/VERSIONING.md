# 版本与发布节奏

> 2026-11-06 起生效。起因：一天内从 v1.3.0 连发到 v1.9.0，版本跨度过快。
> 之后的版本号按本文执行，由维护者（kano）监督。

## 版本号（语义化 1.x.y）

| 变更类型 | 版本动作 | 示例 |
| --- | --- | --- |
| bug 修复、DSH 兼容适配、文案/样式微调 | patch：`1.9.0 → 1.9.1` | 修弹层被面板盖住 |
| 一个成体系的新功能，或一批相关小功能 | minor：`1.9.1 → 1.10.0` | 「供应商编辑 + 获取模型」合在一起 |
| 破坏性变更（配置不兼容、需重新配对、删接口、换 APK 签名） | major：`1.x → 2.0.0` | 不轻易用，用前先说明 |

- APK 与插件版本各自独立：插件按上表走；APK 只在原生层（MainActivity、配对、构建）变化时才动 versionCode/Name。
- ZIP 与 APK 文件名里的版本号必须和 tag、package.json 三处一致。

## 发布节奏

1. **默认攒批**：攒 3–4 个改动（或一周）再发一个版本。单次对话里完成的小修不单独发版，改动留在 main 上，等下一批。
2. **急修例外**：只有两种情况单独发 patch——当前 release 有致命中招（装上就用不了），或维护者明确说"马上要"。
3. **一个 release 一份清单**：说明里列出这一批包含的全部改动，不再一行一个版本。
4. **发版前自检**：`node --check` 全部 JS、`curl /api/health` 为 `ok: true`、真机/模拟器过一遍改动涉及的界面。

## 当前基线

- **v1.9.0**（2026-11-06）：当前最新 release，也是本政策生效时的基线。
- 下一个版本：攒批修复 → `1.9.1`；攒批功能 → `1.10.0`。
